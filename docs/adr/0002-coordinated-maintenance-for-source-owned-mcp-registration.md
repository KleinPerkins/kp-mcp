# ADR 0002: Coordinated maintenance for source-owned MCP registration

Status: Proposed, not accepted. Owner: KleinPerkins/kp-mcp. Date: 2026-11-01.

## Amendment boundary

This proposed successor incorporates the unchanged normative ownership, transport, auth, durability, recovery, API and release requirements of ADR0001 at merged revision a34a0f73b93650e4a6abe9c9dff9a2e3eced94cb (file SHA-256 48fba8b037cf75d0ecd05709c4d9b02ee7b26b7641d9ad9646f727260637e30c). It amends only the concurrency/admission claim, its caller-side maintenance coordination and the versioned records necessary to state that claim. The strict native path remains available and default; no weaker automatic fallback is authorized.

The operator already confirmed the source-owned, field-preserving registrar destination. This proposal requires a distinct owner decision about the explicitly weaker maintenance risk. Draft publication is neither that decision nor implementation or live-operation approval.

## 4. Exact concurrency decision: proposed successor, not acceptance

**Current ADR0001:** every config/state mutation requires a reviewed native conditional replacement or exclusive-write mechanism with provider-issued acquisition evidence, exact target/host/build/mapping binding, freshness and tested release semantics. Registrar locks and pre/post byte checks are drift detection, not exclusion. Only fixture isolation is qualified. Stopping the old mirror is necessary but insufficient. The registrar neither stops apps nor creates an admission/security framework.

| Option | Meets current ADR0001? | Disposition |
|---|---|---|
| Qualified provider conditional replacement or enforced exclusive window | Yes, if actual provider enforcement and evidence meet the existing contract | Retain strict mode. No mechanism was established by the prior bounded audit. This design does not require a new upstream request. |
| Coordinated single-writer maintenance | **No.** Known writers can cooperate, but an unexpected editor/MDM/root/same-user writer can still interleave | **Recommend explicit narrow successor acceptance**, limited to selected local-file operations. This is operational coordination with residual risk, never native exclusivity. |
| Host-managed runtime registration / app-owned connector | May avoid a file write, but does not implement the accepted file receipt/recovery contract by itself | Preserve genuinely external-owned connections. Do not silently switch local registrar entries to another persistence/ownership model or reopen the chosen destination. |

### Proposed changed claim for owner acceptance

> Add an opt-in `coordinated-maintenance` mode for specifically selected local registrar targets. The calling owner coordinates the known writers and proves their agreed pause/handoff states for a bounded operation; the registrar serializes cooperative writes and checks exact target/state preimages and postimages. This mode does **not** guarantee exclusion of a noncooperating writer. An undetected write between the last check and replacement may be overwritten, and a later write may invalidate the observed result. Fail on observed divergence; preserve unresolved journals and require explicit recovery. Keep native-exclusion mode as the strict default, with no automatic downgrade or fallback. Accepting this mode changes only the stated concurrency claim and caller-side coordination, not field ownership, credential boundaries, exact approval, durability, recovery or runtime qualification requirements.

The owner must accept that residual lost-update risk explicitly. A hash check, quiet period, PID list, advisory lock, pause sentinel or an operator statement is evidence of coordination only. None becomes provider acquisition evidence. If a known writer cannot be paused/handed off, refuse that target. Do not merely assume apps are stopped. This includes an identified management writer whose activity cannot be coordinated; unknown or unexpectedly resumed writers remain the disclosed residual risk even after the preconditions pass.

The concrete persisted-contract proposal below is part of the successor decision, not delegated to implementation. Do not add a fourth value to `WriterWindow/v1` silently, label maintenance `native-exclusive-window`, fabricate a provider reference or admit fixture authority. No new generic lease/security service is proposed.

### Proposed closed maintenance contract

All records use the existing canonical encoding, digest, strict unknown-field rejection, private-storage and bounded-identifier conventions. The following are proposed wire contracts, not existing APIs:

- **`kp-mcp/writer-window/v2`:** exactly the v1 fields (`qualification_id`, `qualification_digest`, `issuer_owner`, `issuer_source_revision`, `mechanism`, `host`, `surface`, `build`, `mapping_digest`, `config_target_id`, `state_target_id`, `acquisition_reference`, `acquired_at`, `expires_at`, `release_method`, `schema`) plus required `concurrency_claim` and `maintenance_evidence_digest`. In v2, `mechanism` is exactly `coordinated-maintenance`, `concurrency_claim` exactly `coordinated`, `issuer_owner` exactly `KleinPerkins/dev`, `acquisition_reference` the maintenance UUID, and `release_method` exactly `dev-int014-explicit-handoff/v1`. The qualification id/digest must match the accepted maintenance profile in kp-mcp's reviewed table; the dev issuer revision must match that profile's permitted caller adapter. This is coordination admission, not provider acquisition. Strict native/fixture profiles retain their v1 contract and are never converted implicitly.
- **`dev/mcp-maintenance-evidence/v1`:** closed fields are `schema`, `maintenance_id`, `issuer_source_revision`, `accepted_contract_digest`, `audience_digest`, `config_target_id`, `state_target_id`, `config_preimage_digest`, `state_preimage_digest`, `known_writers`, `consequence_review_digest`, `legacy_handoff_id`, `acquired_at`, `expires_at`, `prior_guard_state`, `prior_guard_lock`, `predecessor_maintenance_id`, `recovery_of`. The last two are null only for a root operation; recovery requires both the predecessor UUID and the existing digest-bound original registrar operation reference. They are immutable and covered by the maintenance digest and new action approval; mismatched, cyclic or competing recovery lineage refuses. The audience is the existing exact owner/connection/host/scope/target/action audience; the relevant config/state preimages bind the initial view, and the registrar's normal journal binds subsequent writes. `prior_guard_state` is `enabled|disabled|not_enrolled`; `prior_guard_lock` is `on|off|not_applicable`. Unknown prior state refuses any operation needing to change it. Timestamps bind the same interval as the writer window, at most 600 seconds. No commands, config values, credentials or raw process output are stored.
- **Per-writer evidence:** `known_writers` is a nonempty list unique by bounded `writer_id`. Each record has exactly `writer_id`, `kind`, `prior_state`, `observed_state`, `observation_reference`, `observation_digest`, `observed_at`, `resume_disposition`. `kind` is `legacy-mirror|kit-lifecycle|native-client|editor|server-guard|management`; `prior_state` is `active|inactive|not_enrolled`; admissible `observed_state` is `paused|inactive`; `resume_disposition` is `restore_prior|remain_suspended`. Absence from this list is not proof that a writer cannot exist. The source-pinned dev validator resolves current supported pause/drain observations and the exact consequence review, including no excluded-runtime effects; a boolean, PID list, opaque reference or matching hash alone cannot validate them. Unknown/active writer or unbounded pause effects refuse admission. Target-specific known-writer coverage is established in the later operation packet, never invented here.
- **Handoff and approval:** `legacy_handoff_id` must equal `maintenance_id`: it references this same exact dev-owned evidence and lifecycle state, not another undefined handoff format. Its known-writer rows must cover all applicable old entrypoints under the reviewed caller profile and verify their suspension/drain. `MigrationEvidence/v1.retiring_writer_handoff` must equal this id for adoption; validate the record, required writer coverage and target binding, not just a nonempty string. The maintenance record is not user approval. Existing `Approval/v1` audience/operation/action/payload/timestamp fields remain; a new recognized issuer `dev/int014-operation-approval/v1` is validated by the kp-mcp-owned adapter against the caller's exact operation-bound approval. It must cover the maintenance claim, consequence review and prepared payload. Fixture issuers cannot authorize this mode. No cryptographic or same-user security guarantee is added.
- **Private coordinator lifecycle:** `dev/mcp-maintenance-state/v1` has exactly `schema`, `maintenance_id`, `evidence_digest`, `predecessor_maintenance_id`, `status`, `last_observed_at`, `registrar_result_reference`, `baseline_handoff_reference`, `release_observation_digest`. The predecessor equals the embedded evidence's predecessor (null only at a root). References are digest-bound bounded records, never guessed paths. Status is `acquired|applied_pending_handoff|recovery_required|released|release_failed|cancelled`. Only `acquired`, with fresh validated evidence, admits a new registrar mutation. Allowed edges are `acquired -> applied_pending_handoff|recovery_required|cancelled|release_failed`; `applied_pending_handoff -> released|recovery_required|release_failed`; `release_failed -> released|cancelled|recovery_required` after fresh observed release/restoration checks, without a registrar write under the failed record; and `recovery_required -> released|cancelled` only upon a matching verified child terminal result. `recovery_required` admits no same-record write or renewal: a new approved child record must resolve it; only a verified child terminal result may transition the predecessor to `released` or `cancelled`, without replaying its mutation. Terminal `released`/`cancelled` have no outgoing edges. All other edges refuse.
- **Per-status completeness:** `acquired` requires all three result/handoff/release references null. `applied_pending_handoff` requires a verified registrar terminal result and null release observation; baseline proof may remain null while pending. `recovery_required` may retain null results after an interruption, but never fabricates or discards an existing result. `released` requires a verified registrar (or resolving child) terminal result, compatible baseline proof or explicit not-applicable proof, and successful allowed resume/release observations. `cancelled` requires a no-registrar-mutation proof or exact approved cancellation/recovery result, baseline unchanged/restored/not-applicable proof, and successful allowed restoration observations. `release_failed` requires a failure observation digest and retains every already-established registrar/baseline reference. Terminal and child proofs must match the audience, targets, pre/postimages and lineage. No status permits automatic old-writer rearm; successful adoption keeps its legacy writers suspended even after the maintenance window is released.
- **Evidence delivery and fresh validation:** `RegistrationContext/v2` embeds the full closed, redacted `maintenance_evidence` object privately, and `prepared-record/v2` persists that exact context. It is hashed into `WriterWindow/v2` and the prepared payload; a UUID/digest without those bytes refuses. The fixed maintenance validator identity is `dev/int014-maintenance-validator/v1`. The dev caller reconstructs its source-pinned validator from the reviewed `_ops/interoperability/mcp_maintenance.py` implementation on every fresh process; kp-mcp accepts it only through its reviewed `writer_window.py` validator binding for that exact identity/source revision. It is a runtime object, never a serialized callable or arbitrary import/command. Missing/wrong validator refuses, including direct kit calls. The validator loads the exact current UUID-bound lifecycle record from dev's private maintenance store, rehashes the embedded evidence, verifies the accepted contract/issuer, audience/targets/preimage bindings, acquired state, expiry and predecessor relation, and re-observes the supported known-writer/consequence conditions. The registrar checks the appropriate initial or journal-phase expected bytes before every prepare/apply/recover/rollback/cancel mutation; it does not compare every phase against obsolete initial bytes after its own verified write. Source, evidence or live-state mismatch refuses. Durable replay uses this same path in `durable_validation.py`, never trust in a persisted 'validated' flag. This remains cooperative operational validation, not exclusion against a dishonest same-user actor or unknown writer.
- **Persistence/provenance:** the maintenance path uses explicit v2 schemas for registration context, preview, prepared operation and its persisted `prepared-record`, registrar journal, terminal and result. They preserve their v1 field sets and carry required `concurrency_claim=coordinated`, `writer_window_digest` and `maintenance_evidence_digest` wherever the context or outcome is persisted; all three are bound by payload/action/journal/terminal digests. The context embeds the v2 window. Definition/auth/migration records and leaf-ownership snapshots keep their v1 meaning and are linked by exact digest. A new v2 operation may link a prior v1 ownership receipt, but may not replay an old v1 operation under weaker protection. Old adapters reject v2; new adapters validate each version separately, including interrupted inverse recovery. Results keep existing reason/outcome codes (`concurrency_unqualified`, `approval_invalid`, `stale_preview`, `recovery_required`, `writer_release_failed` as applicable); no `native_exclusion` claim can be emitted for maintenance. Registrar apply success and the coordinator's baseline/release status remain separately visible.

These are fixed proposed choices for D0 review/acceptance. The operator is deciding the bounded risk contract including this evidence/lifecycle design, not being asked to select serialization details later.

The two owners also need to reconcile the integration plan's “no competing writer” gate: in this mode it means known designated source writers have handed off and are not concurrently active during the operation, with the above explicit residual risk. This is a semantic qualification to the accepted integration contract, not an unannounced edit to a mutable status field. Frozen ADR0001 and the accepted integration plan remain unchanged until their governed successors are accepted.


## Required scope and preservation

Maintenance consequences must be bounded before any host shutdown or client-wide pause. Refuse any operation that could stop, restart, mutate or otherwise affect an excluded runtime, or whose scope is unknown; do not inspect an excluded runtime or invent an exception. The initial operation must classify every byte it would persist in prepared or recovery material as eligible non-secret data under existing authority. A non-secret selected entry does not classify the rest of its file. INT008 KEEP_NO_COPY_UNQUALIFIED remains unchanged; no secret-bearing copy or remediation is authorized.

Server-guard remains an independent recovery owner using its existing operator workflows, not a provider of exclusion or discovery. Configuration, registrar state and baseline handoff are not one atomic transaction. The execution plan must require truthful separate outcomes and preserve the exact rollback conditions inherited from ADR0001.

## Consequences

A noncooperating writer can still cause an undetected lost update. The mode trades that residual risk for a bounded coordinated route without inventing an unavailable host API. Known writers that cannot be coordinated, uncertain pause effects, stale evidence, unclassified durable material and incompatible baseline handoff remain target-specific refusals. Accepting this proposal does not accept a server-guard augmentation, retire a writer, install packages, activate a connection or authorize service calls. Dev must obtain the corresponding integration-contract amendment before using this mode.
