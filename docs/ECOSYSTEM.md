# kp-mcp Agent Ecosystem

How agents discover and use kits in this monorepo.

---

## What is a kit?

A kit is a standalone Python package that exposes a set of capabilities (ops) over two surfaces simultaneously:

- **CLI** — typed commands (`<domain>-kit <svc> <op> --arg value`) that output `{status, op, data, meta}` JSON.
- **MCP stdio** — Model Context Protocol server (`<domain>-kit mcp`) that exposes the same ops as MCP tools.

Both surfaces derive from one registry. Adding an op once makes it available in both.

## Agent setup (one-time per kit)

Bootstrap 0.3.0 requires owner-supplied context, exact prepared bytes and
operation approval. Its only qualified writer mechanism is disposable fixture
isolation. The ordinary `google-kit bootstrap`, `snow-kit setup` and other kit
CLIs report missing authority and leave client files unchanged. No CLI option
can grant fixture status to a live path.

Native writer exclusion, ownership adoption and live migration remain separate
owner gates. Snow validates the registration batch before any profile repair;
Google registration no longer repairs style profiles. See the
[Google quickstart](../google-kit/docs/QUICKSTART.md) and
[Snow quickstart](../snow-kit/docs/QUICKSTART.md) for the source-version boundary.

## How agents discover capabilities

### 1. Capability INDEX (intent → card)

Each kit maintains an `INDEX.md` that maps intents to capability cards:

```
google-kit/docs/INDEX.md    — capability index for every google-kit op
snow-kit/docs/INDEX.md      — capability index including the MCP help meta-tool
snow-kit/docs/INTENTS.md    — deterministic Snow intent/workflow manifest
widget-kit/docs/INDEX.md    — capability index for every widget-kit op
```

Query the index to find the right op for an intent (e.g. "list calendar events" → `calendar.list`). Live op/service counts are in [CATALOG.md](CATALOG.md).

### 2. Capability cards

Each op has a generated card at `<domain>-kit/docs/cards/<svc>.<op>.md`. Cards contain:
- Input schema (field names, types, required/optional, defaults)
- Output schema (`data` fields)
- Posture (`read` / `write` / `destructive` / `admin`)
- OAuth scopes required
- Performance / quota metadata
- Errors + retry behavior
- Runnable CLI + MCP example

### 3. MCP tool schema

`<domain>-kit/docs/schemas/<svc>.<op>.json` — JSON schema for each MCP tool, generated deterministically from the registry. Load via the `_manifest.json` to enumerate all tools.

## Auth and bootstrap

Kits use platform-secure credential storage — no tokens in repositories,
registrations, or tool arguments. Google-kit uses macOS Keychain; snow-kit uses
external-browser SSO plus Snowflake connector secure local storage.

Google-kit auth flow:
1. Import OAuth credentials: `google-kit auth import` (stores client_id / client_secret in Keychain)
2. Run PKCE OAuth: `google-kit auth login` (stores access_token / refresh_token in Keychain)
3. Verify: `google-kit auth status`

The `kp-mcp-bootstrap` package provides the shared auth engine:
- `kp_mcp_bootstrap.secrets.SecretStore` — Keychain read/write
- `kp_mcp_bootstrap.oauth.run_pkce_flow()` — PKCE loopback flow
- `kp_mcp_bootstrap.detect.detect_env()` — active agent platform detection
- `kp_mcp_bootstrap.registrars.*` — owned-field preview and approved transactions;
  bootstrap 0.3.0 qualifies only disposable fixtures for writes

## Safety rules

Each kit ships a Cursor rule file at `<domain>-kit/rules/<domain>-kit-mcp-safety.mdc`. Load the relevant rule when using that kit's MCP tools.

Posture metadata is shared, but each kit's server-side gates are decisive:

| Posture | Confirmation | Retry |
|---------|-------------|-------|
| `read` | No mutation confirmation | Kit-specific; snow-kit does not auto-retry tool calls |
| `write` | Explicit operator confirmation/gates | Only when the kit proves retry safety |
| `destructive` | Always, each call | Never by default |
| `admin` | Always, each call | Never by default |

Never pass credentials as tool arguments. Google-kit uses Keychain; snow-kit
uses external-browser SSO plus Snowflake connector secure local storage.

## Response envelope

Every current kit op returns a typed envelope with operation data, warnings,
and metadata. Google-kit may also include pagination:

```json
{
  "data": { ... },
  "warnings": [],
  "meta": {
    "run_id": "uuid",
    "op": "gmail.list"
  }
}
```

Record `meta.run_id` in any escalation or triage report to correlate CLI and MCP calls in the audit log.

## Error taxonomy

| Error class | Agent action |
|-------------|-------------|
| Google API `Transient` / `QuotaRateLimit` | Google-kit's API wrapper applies its documented bounded retry policy |
| Snowflake `Transient` | Snow-kit does not auto-retry a tool call; retry once only when the operation is idempotent |
| `Auth` | Stop; use the kit's sign-in flow |
| `Permission` | Stop; do not retry unchanged |
| `Validation` | Fix input; retry once |
| Snow-kit `Unavailable` | Repair the configured source; never interpret it as an empty result |
| `Timeout` | Narrow the request; no automatic retry |
| `Unknown` | Escalate immediately |

Full triage runbook: [docs/dev/TRIAGE.md](dev/TRIAGE.md).
